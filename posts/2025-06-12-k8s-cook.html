  name: admin-user

---
apiVersion: rbac.authorization.k8s.io/v1
 kind: ClusterRoleBinding
 metadata:
  name: admin-user
 roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
 subjects:- kind: ServiceAccount
  name: admin-user
  namespace: kubernetes-dashboard
  • そのアカウントで認証トークンを作成する必要

  • ダッシュボードにCPU, メモリの使用状況が出ることを確認
  • あるいはkubectl top pods -A, kubectl top nodes

3. Kubernetesクライアントの使い方を学ぶ

3.1. リソースの一覧表示

  • すべてのサービスとデプロイメントを⼀覧表⽰
    • kubectl get services,deployments
  • オートコンプリートを有効にすることが重要

省略名

  • configmaps（別名 cm）
  • daemonsets（別名 ds）
  • deployments（別名 deploy）
  • endpoints（別名 ep）
  • events（別名 ev）
  • horizontalpodautoscalers（別名 hpa）
  • ingresses（別名 ing）
  • namespaces（別名 ns）
  • nodes（別名 no）
  • persistentvolumeclaims（別名 pvc）
  • persistentvolumes（別名 pv）
  • pods（別名 po）
  • replicasets（別名 rs）
  • replicationcontrollers（別名 rc）
  • resourcequotas（別名 quota）
  • serviceaccounts（別名 sa）
  • services（別名 svc）

3.2. リソースの削除

  • 名前空間my-app内のすべてのリソースと名前空間⾃体を削除
kubectl get ns
kubectl delete ns my-app

# app=niceoneラベルが付いたサービスとデプロイメントを削除
kubectl delete svc,deploy -l app=niceone

# hangingpodという名前のポッドを強制的に削除
kubectl delete pod hangingpod --grace-period=0 --force

# 名前空間test内のすべてのポッドを削除
kubectl delete pods --all --namespace test
  • PodやReplicasetなどは削除しない
    • Deploymentを通じて削除する
  • カスケード削除と直接削除を考慮する

3.3. kubectl によるリソース変更の監視

  • --watchオプション
    • kubectl get pods --watch
    • watch kubectl get pods
  • 出力のフォーマットが違う

3.4. kubectl を使用したオブジェクトの編集

 $ kubectl run nginx --image=nginx
 $ kubectl edit pod/nginx

 # EDITORまたはKUBE_EDITOR環境変数
$ export EDITOR=vi
  • 全ての変更が更新をトリガーするわけではない

3.5. kubectl にリソースとフィールドの説明を求める

  • kubectl explain svc
    • APIサーバのOASからリソースとフィールドを取得

4.6. デプロイメントの更新

  • デプロイメントを更新し、デフォルトの更新戦略RollingUpdateロールアウトを⾃動的に処理
 $ kubectl create deployment myapp --image=gcr.io/google-samples/hello-app:1.0

 $ kubectl set image deployment/myapp \
    hello-app=gcr.io/google-samples/hello-app:2.0

 $ kubectl rollout status deployment myapp

 # yamlを編集
 $ kubectl edit deploy myapp

 $ kubectl rollout history deployment myapp
REVISION        CHANGE-CAUSE
 1               <none>
 2               <none>
 3               <none>
  • 上記ではリビジョン3にロールアウトされている
  • しかし、CHANGE_CAUSEは空
$ kubectl annotate deployment/myapp \
 kubernetes.io/change-cause="Added port definition."

 # 特定のキーを更新
 kubectl patch deployment myapp -p '{"spec": {"template":
 {"spec": {"containers":
 [{"name": "sise", "image": "gcr.io/google-samples/hello-app:2.0"}]}}}}'

 # リビジョン2にロールバック
 $ kubectl rollout undo deployment myapp --to-revision 2
  • レプリカ数などの要素の変更では、新しいデプロイメントはトリガーされない

4.7. バッチジョブの実行

# 作成されたPodも削除される

$ kubectl patch cronjob.batch/hourly-date --type=strategic \
--patch '{"spec":{"suspend":true}}'

5. サービスの利用

  • Podがクラスター内で通信する方法、互いを検出する方法、外部からアクセスする方法
  • kube-proxy
    • 全てのノードで実行されるプロセス
    • API サーバーにクエリを実⾏してクラスター内の新しいサービスについて学習
    • ノードのiptablesを更新して、必要なルーティング情報を提供

5.1. アプリケーションを公開するサービスの作成

$ kubectl expose deploy/nginx --port 80
$ kubectl describe svc/nginx
  • 上記ではClusterIPが作成される
  • ブラウザ経由でアクセス
kubectl proxy
open http://localhost:8001/api/v1/namespaces/default/services/nginx/proxy/
  • サービスが正常に動作しない場合
    • セレクター内のラベルを確認
    • kubectl get endpoints <service-name>で確認
    • 生成されていない場合、ポッドを見つけられていない可能性
  • k8sはServiceを利用し、全てのノードのiptablesを動的に構成

5.2. サービスの DNS エントリーの確認

  • Serviceが作成したDNS登録を確認
    • $SERVICENAME.$NAMESPACE.svc.cluster.local
    • 完全修飾ドメイン名
  • nslookup nginx
    • 例：nginx.default.svc.cluster.local
    • 同じ名前空間でないと、結果を返さない

5.3. サービスのタイプの変更

  • LoadBalancerタイプはコストがかかる可能性

5.4. Ingress コントローラーのデプロイ

  • リバースプロキシ、LBとして機能

  • ホスト名、URIパスで変更できる

  • Ingressコントローラをデプロイ
$ kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/
 controller-v1.8.1/deploy/static/provider/cloud/deploy.yaml
  • 新しく作成されたingress-nginx名前空間で新しいポッドが起動
    • kubectl get pods -n ingress-nginx
  • k8s Gateway APIの新しい仕様がIngress仕様の将来的な代替として登場
    • 今後はこちらを検討する価値がある

5.5. クラスターの外部からサービスにアクセスできるようにする

  • hello-appサービスへのURI パス/webを構成するIngressオブジェクト
 apiVersion: networking.k8s.io/v1
 kind: Ingress
 metadata:
  name: nginx-public
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
 spec:
  ingressClassName: nginx
  rules:
  - host:
    http:
      paths:
      - path: /web
        pathType: Prefix
        backend:
          service:
            name: web
            port:
              number: 8080
  • ダッシュボードで確認できる
  • 上記の場合は、プライベートIPアドレス
  • IngressコントローラーはAPIサーバーの/ingressesエンドポイントをリッスン
  • kubectl describe ingress

6. アプリケーションマニフェストの管理

  • Helm, kompose, kappなどのツール
  • kompose
    • docker-composeをk8sに変換
  • kapp
    • 複数のyamlを一個のアプリケーションとして管理

6.1. Kubernetes パッケージマネージャーである Helm のインストール

  • brew install helm

6.2. Helm へのチャートリポジトリの追加

  • Artifact Hubなどが有名
    • helmコマンドは上記と統合
# 検索
helm search hub --list-repo-url redis

# Bitnamiによって公開されたチャートをデプロイする場合
helm repo add bitnami https://charts.bitnami.com/bitnami

6.3. Helm を使用したアプリケーションのインストール

  • Redisチャートをデプロイする場合
  • helm repo update
    • 検索の前に、チャートリポジトリのローカルキャッシュを更新
helm search repo bitnami/redis
helm install redis bitnami/redis
kubectl get all -l app.kubernetes.io/name=redis
  • helm installコマンドの出力に注意
    • シークレット情報が含まれている可能性
  • helm list, helm status name

6.4. チャートのカスタマイズ可能なパラメーターの検査

  • Valuesファイルの確認
    • helm show values bitnami/redis
  • Readmeの表示
    • helm show readme bitnami/redis

6.5. チャートパラメータの上書き

helm install redis bitnami/redis --set architecture=standalone
helm install redis bitnami/redis --values values.yaml
  • yamlにはarchitecture: standaloneを含める

6.6. ユーザー指定のパラメータの取得 Helm リリース

  • helm get values redis
  • helm getでは、YAML、フックなども取得できる

6.7. Helm を使用したアプリケーションのアンインストール

  • helm uninstall redis

6.8. パッケージ化するための独自のチャートの作成 Helm によるアプリケーション

  • helm createとhelm packageコマンドを使⽤
$ tree oreilly/
 oreilly/
 ├── Chart.yaml
 ├── charts
 ├── templates
 │   ├── NOTES.txt
 │   ├── _helpers.tpl

# チャートをローカルでテスト
helm install oreilly-app ./oreilly

helm package oreilly/

# チャートをリポジトリに公開
# 以下はindex.yamlを生成
helm repo index .

helm search repo oreilly

   hard:

 $ kubectl apply -f resource-quota-pods.yaml --namespace=my-app
 $ kubectl describe resourcequota podquota --namespace=my-app

8.1. コンテナ間でのデータ交換 ローカルボリューム

  • Pod内で2つのコンテナを実行し、データを交換したい
apiVersion: v1
kind: Pod
metadata:
  name: sharevol
 spec:
  containers:
  - name: c1
    image: ubuntu:20.04
    command:
      - "bin/bash"
      - "-c"
      - "sleep 10000"
    volumeMounts:
      - name: xchange
        mountPath: "/tmp/xchange"
  - name: c2
    image: ubuntu:20.04
    command:
      - "bin/bash"
      - "-c"
      - "sleep 10000"
    volumeMounts:
      - name: xchange
        mountPath: "/tmp/data"
  volumes:
  - name: xchange
    emptyDir: {}
