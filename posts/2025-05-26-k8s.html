2.コンテナの作成と実行

  • Open Container InitiativeがOCIイメージ形式で標準化している

コンテナイメージ

  • ローカルからイメージをビルド
  • コンテナレジストリからイメージをダウンロード
  • イメージは複数のレイヤーで構成されている
    • 各レイヤーからファイルを追加、削除、変更

コンテナの設定

  • ネットワークの設定⽅法
  • 名前空間の分離⽅法
  • リソース制約(cgroup)
  • コンテナインスタンスにどのようなsyscall制限を設定するか

Dockerでアプリケーションイメージを構築する

ドッカーファイル
  • .dockerignoreファイルの追加を忘れずに 
    node_modules
画像サイズを最適化する
  • イメージの大きさを常に気にする
  • 後続のレイヤーによって削除されたファイルは実際にはイメージに含まれることに注意
    • ただアクセスできないだけ
    • プルするたびに、ネットワークを介して送信されてしまう
  • レイヤーを変更するたびに、そのあとのレイヤーもすべて変更される
    • 前のレイヤーを変更すると、後ろのレイヤーを再構築、プルする必要
    • npm installとcp server.js .のどちらを先に書くべきか？
      • server.jsが変更された場合を考える
      • nodeパッケージを後に書くと、server.jsの変更ごとにプルする必要
        • 変更される可能性の低いものから書く
イメージ・セキュリティー
  • 例えば、PWを含んだコンテナを作らない
  • 一個のレイヤーでファイルを削除しても、その前のレイヤーからは削除されない
  • イメージは実行することが目的なので、最小化が重要
    • 不要なライブラリなど、無駄な脆弱性を残さない

多段階イメージビルド

  • 大きいイメージはデプロイが遅くなる ```dockerfile …

FROM alpine USER nobody:nobody COPY –from=build /go/bin/kuard /kuard CMD [ “/kuard” ]

- ビルドイメージとデプロイイメージで分ける
- 500MB→20MBまでこの例では削減できた
  - デプロイ時間の大幅な短縮

マルチステージビルドは有名ですが、ここまでサイズが変わるとは思いませんでした。また、`USER`や`ENV`はあまり使用したことがなかったので意識したいです。

パブリッククラウドプロバイダにKubernetesをインストールする

     $ kind create cluster --wait 5m

Kubernetesクライアント

クラスタの状態をチェックする
$ kubectl get componentstatuses
  • schedulerとetcdサーバーを確認できる
  • Healthyとなっていることを確認
Kubernetesノードをリストアップする
  • kubectl get nodes→kubectl describe nodesの流れ
    • labels: ARMプロセッサやOS情報
    • Conditions: 操作の情報
    • Capacity: 容量
    • System-info
    • Non-terminated pods: ポッド情報
      • kube-dnsなどを確認できる

4.一般的なkubectlコマンド

名前空間

  • デフォルトは、default名前空間と対話
  • --all-namespaces
    • クラスター内の全てのポッドの一覧表示など

コンテクスト

  • $HOME/.kube/configファイル
  • set-contextだけでなく、use-contextまで必要
  • set-contextコマンドで、--users, --clustersフラグの使用
    • 異なるクラスタ、ユーザでの認証

Kubernetes APIオブジェクトを表示する

  • k8sリソースはRestFulリソースを提供
    • kubectlはこのURLにHTTP要求をし、パスに存在するオブジェクトにアクセス
  • -o wide: 詳細
  • -o json | yaml
  • kubectlの出力でヘッダーを削除することが一般的
    • awkコマンドと組み合わせる
  • オブジェクトから特定のフィールドを抽出
    • JSONPathクエリ言語の使用
      • 指定されたPodのIPアドレスを抽出して出⼒するコマンド 
        $ kubectl get pods my-pod -o jsonpath --template={.status.podIP}
  • --watchオプション

Kubernetesオブジェクトを作成、更新、破棄する

  • --dry-run: サーバに送信せずターミナル出力
  • kubectl edit: 定義を含むエディターが起動
  • delete -f, delete resource name: 削除

オブジェクトにラベルと注釈を付ける

  • labelコマンドとannotateコマンド
  • barという名前のPodにcolor=redラベルを追加するコマンド
    • ` $ kubectl label pods bar color=red`
  • --overwriteフラグで上書き
  • ラベル名-でラベルの削除

デバッグ・コマンド

  • Podに複数のコンテナがある場合は-cでコンテナを選択
  • logsとexec -it --bashコマンド
  • bashがない場合は、kubectl attach -it pod
  • kubectl port-forward <pod-name> 8080:80
    • ローカルのポート8080:リモートの80
  • kubectl get events
    • --watch
    • 全ての名前空間は-A
  • kubectl top pods

クラスター管理

コマンド自動補完

  • brew install bash-completion
  • macOSでは${HOME}/.bash_profileファイルに追記

クラスターの別の見方

  • Rancher DashboardやHeadlampプロジェクトなど
  • kubectl helpコマンド

5.ポッド

KubernetesにおけるPod

  • 各コンテナは独自のcgroupで実行されるが、いくつかのLinux名前空間を共有
  • 同じPodで実行されるアプリ
    • 独自のIPアドレスとネットワーク空間を共有する

Podを使って考える

  • WordPressとMySQLを同じPodに置くのはアンチパターン

ポッド・マニフェスト

  • 宣言型構成は多くの利点がある
    • 可読性、レビューのしやすさ、文章化など
ポッドを作成する
$ kubectl run kuard --generator=run-pod/v1 \
  --image=gcr.io/kuar-demo/kuard-amd64:blue
$ kubectl get pods # pending
$ kubectl delete pods/kuard

コマンドで作成することはあまりないと思いますが、一応オプションなども覚えておきたいです。

リスト・ポッド

  • ` $ kubectl describe pods kuard`
    • ラベル、アノテーション、IP、ポート、イメージなどを確認できる

ログでより多くの情報を得る
execを使ってコンテナ内でコマンドを実行する
コンテナとの間でファイルをコピーする
  • コンテナへのファイルのコピーはアンチパターン
    • ただし、緊急時には仕方がない
    • すぐにイメージのビルドを行うべき

正常性確認

  • デフォルトでは、メインプロセス軌道を確認するだけ
ライブネス・プローブ
      livenessProbe:
        httpGet:
          path: /healthy
          port: 8080
        initialDelaySeconds: 5
        timeoutSeconds: 1
        periodSeconds: 10
        failureThreshold: 3
  • httpGetプローブの使用
  • コンテナ起動5行後から呼び出される
  • 1秒以内に応答する必要(200-400)
  • 3回連続失敗でコンテナは再起動 
    kubectl port-forward kuard 8080:8080
  • ブラウザで、http://localhost:8080にアクセス
    • Liveness Probeを選択
    • コンテナを再起動できる
  • 実際の再起動の動作はPodのrestartPolicyで決定される
    • Always, onFailure, Never
レディネスプローブ
  • 稼働状態と準備状態を区別する
    • readinessプローブとliveness プローブを組み合わせる
スタートアップ・プローブ
  • スロースタートコンテナを管理する代替⽅法
高度なプローブ設定
  • プローブを開始するまでの待機時間
  • 真の失敗と⾒なすべき失敗の数
  • 失敗数をリセットするために必要な成功の数など
その他の正常性確認型チェック
  • tcpSocketヘルスチェックもサポート
    • 非HTTPアプリで役立つ
  • execプローブ
    • スクリプトが0コードを返した場合に成功
    • カスタムアプリ検証ロジックに役立つ

リソース管理

リソースの要求最低限必要なリソース
  • CPUとメモリを考える
  • CPU半分以上、128メモリ以上のリクエストの例 
    resources:
requests:
  cpu: "500m"
  memory: "128Mi"
  • requestsは最小値であることに注意

k8sでもdocker-compose.yamlみたいに書けるのは知りませんでした。

リソースの使用量を制限する
      resources:
        requests:
          cpu: "500m"
          memory: "128Mi"
        limits:
          cpu: "1000m"
          memory: "256Mi"
  • 1000m = 1.0CPU

ボリュームでデータを永続化する

  • Podの削除、再起動でファイルシステムのデータも消える
    • ステートレスWebアプリでは問題ない
Podでボリュームを使用する
  • spec.volumes, container.volumeMountsの編集
  • pod内の異なるコンテナは、異なるマウントパスで同じボリュームをマウントできる
apiVersion: v1
kind: Pod
metadata:
  name: kuard
spec:
  volumes:
    - name: "kuard-data"
      hostPath:
        path: "/var/lib/kuard"
  containers:
    - name: kuard
      image: gcr.io/kuar-demo/kuard-amd64:blue
      volumeMounts:
        - mountPath: "/data"
          name: "kuard-data"
      ports:
        ...
Podでボリュームを使うさまざまな方法
  • 真に永続的なデータの保存
    • NFS, iSCSIのプロトコル
    • EBSなど
  • NFSサーバの例 ```yaml volumes:
    • name: “kuard-data” nfs: server: my.nfs.server.local path: “/exports” ```

すべてをまとめる

  • 永続ボリューム、レディネスプローブとライブネスプローブ、リソース制限の組み合わせ ```yaml apiVersion: v1 kind: Pod metadata: name: kuard spec: volumes:
    • name: “kuard-data” nfs: server: my.nfs.server.local path: “/exports” containers:
    • image: gcr.io/kuar-demo/kuard-amd64:blue name: kuard ports:
      • containerPort: 8080 name: http protocol: TCP resources: requests: cpu: “500m” memory: “128Mi” limits: cpu: “1000m” memory: “256Mi” volumeMounts:
      • mountPath: “/data” name: “kuard-data” livenessProbe: httpGet: path: /healthy port: 8080 initialDelaySeconds: 5 timeoutSeconds: 1 periodSeconds: 10 failureThreshold: 3 readinessProbe: httpGet: path: /ready port: 8080 initialDelaySeconds: 30 timeoutSeconds: 1 periodSeconds: 10 failureThreshold: 3 ```
