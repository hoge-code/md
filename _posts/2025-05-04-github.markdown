### 1. GitHub の Pull RequestとIssue テンプレート

#### テンプレートの設置方法

`.github/` ディレクトリ以下に以下のように配置すると、自動でテンプレートとして認識されます。

```
.github/
├── PULL_REQUEST_TEMPLATE.md
├── ISSUE_TEMPLATE/
│   ├── bug_report.md
│   ├── feature_request.md
│   └── config.yml
```

#### Pull Request テンプレート例

```md
## 概要

## 変更内容

## 関連Issue

Fixes #123

## 動作確認手順
```

---

#### Issue テンプレート（例: `bug_report.md`）

```yaml
name: Bug Report
description: バグの報告
title: "[BUG] "
labels: [bug]
body:
  - type: textarea
    attributes:
      label: 概要
  - type: textarea
    attributes:
      label: 再現手順
```

### 2. Issue からブランチを作成 

VSCodeなら`GitHub PullRequest + Issue`という拡張機能を利用して、Issueからブランチを作成できます。ブランチにはIssue番号を含めることがありますが、コミット名にIssue番号を書かない限り、Issueが自動でクローズされることがないことに注意します。

#### 例：

```bash
git checkout -b feature/123-add-login
```

#### Issue をクローズするコミットメッセージの書き方

* `Fixes #123`
* `Closes #123`
* `Resolves #123`

GitHub 上でこのコミットが PR にマージされると、該当 issue が自動でクローズされます。

### 3. Conventional Commit & 自動リリースノート生成

取り敢えず`Conventional Commit`に従っておけば、`GitHub Copilot`での補完、リリースノートの自動生成などのメリットが得られます。コミットメッセージが`Conventional Commit`に従っているか確認するためにフックを使用することもできます。

```text
<type>(<scope>): <subject>
```

#### 例：

```text
feat(auth): ログイン機能を追加
fix(api): 500エラーの原因を修正
docs(readme): セットアップ手順を追加
```

---

#### 自動リリースノート生成

`semantic-release`など`を使うと、PRやコミットから changelog や GitHub Release を自動生成することができます。

1. `semantic-release` をインストール
2. `release.config.js` でルールを定義
3. GitHub Actions に `semantic-release` ワークフローを追加


### 4. 前回のコミットに少しだけ変更を追加

コミットメッセージの変更で紹介される`amend`コマンドですが、直前のコミットに変更を付け足す場面で使用することのほうが多い気がします。プッシュした後だと、`git push --force`する必要があります。

```bash
git commit --amend --no-edit
```
