#### 2.6. Kubernetes ダッシュボードへのアクセス

- クラスターを管理する権限を持つServiceAccountを作成する必要

```yaml
apiVersion: v1
 kind: ServiceAccount
 metadata:
  name: admin-user
  namespace: kubernetes-dashboard
---
apiVersion: rbac.authorization.k8s.io/v1
 kind: ClusterRoleBinding
 metadata:
  name: admin-user
 roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
 subjects:- kind: ServiceAccount
  name: admin-user
  namespace: kubernetes-dashboard
```

- そのアカウントで認証トークンを作成する必要
    - `kubectl -n kubernetes-dashboard create token admin-user`

### 3. Kubernetesクライアントの使い方を学ぶ

#### 3.1. リソースの一覧表示

- すべてのサービスとデプロイメントを⼀覧表⽰
    - `kubectl get services,deployments`
- オートコンプリートを有効にすることが重要

**省略名**
- `configmaps`（別名 `cm`）
- `daemonsets`（別名 `ds`）
- `deployments`（別名 `deploy`）
- `endpoints`（別名 `ep`）
- `events`（別名 `ev`）
- `horizontalpodautoscalers`（別名 `hpa`）
- `ingresses`（別名 `ing`）
- `namespaces`（別名 `ns`）
- `nodes`（別名 `no`）
- `persistentvolumeclaims`（別名 `pvc`）
- `persistentvolumes`（別名 `pv`）
- `pods`（別名 `po`）
- `replicasets`（別名 `rs`）
- `replicationcontrollers`（別名 `rc`）
- `resourcequotas`（別名 `quota`）
- `serviceaccounts`（別名 `sa`）
- `services`（別名 `svc`）

#### 3.2. リソースの削除

- 名前空間my-app内のすべてのリソースと名前空間⾃体を削除

```bash
kubectl get ns
kubectl delete ns my-app
```

```bash
# app=niceoneラベルが付いたサービスとデプロイメントを削除
kubectl delete svc,deploy -l app=niceone

# hangingpodという名前のポッドを強制的に削除
kubectl delete pod hangingpod --grace-period=0 --force

# 名前空間test内のすべてのポッドを削除
kubectl delete pods --all --namespace test
```
- PodやReplicasetなどは削除しない
    - Deploymentを通じて削除する
- カスケード削除と直接削除を考慮する

#### 3.3. kubectl によるリソース変更の監視

- `--watch`オプション
    - `kubectl get pods --watch`
    - `watch kubectl get pods`
- 出力のフォーマットが違う

#### 3.4. kubectl を使用したオブジェクトの編集

```bash
 $ kubectl run nginx --image=nginx
 $ kubectl edit pod/nginx

 # EDITORまたはKUBE_EDITOR環境変数
$ export EDITOR=vi
```
- 全ての変更が更新をトリガーするわけではない

#### 3.5. kubectl にリソースとフィールドの説明を求める

- `kubectl explain svc`
    - APIサーバのOASからリソースとフィールドを取得

#### 4.6. デプロイメントの更新

- デプロイメントを更新し、デフォルトの更新戦略RollingUpdateロールアウトを⾃動的に処理

```bash
 $ kubectl create deployment myapp --image=gcr.io/google-samples/hello-app:1.0

 $ kubectl set image deployment/myapp \
    hello-app=gcr.io/google-samples/hello-app:2.0

 $ kubectl rollout status deployment myapp

 # yamlを編集
 $ kubectl edit deploy myapp

 $ kubectl rollout history deployment myapp
REVISION        CHANGE-CAUSE
 1               <none>
 2               <none>
 3               <none>
```

- 上記ではリビジョン3にロールアウトされている
- しかし、`CHANGE_CAUSE`は空

```bash
$ kubectl annotate deployment/myapp \
 kubernetes.io/change-cause="Added port definition."
```

```bash
 # 特定のキーを更新
 kubectl patch deployment myapp -p '{"spec": {"template":
 {"spec": {"containers":
 [{"name": "sise", "image": "gcr.io/google-samples/hello-app:2.0"}]}}}}'

 # リビジョン2にロールバック
 $ kubectl rollout undo deployment myapp --to-revision 2
```

- レプリカ数などの要素の変更では、新しいデプロイメントはトリガーされない

### 5. サービスの利用

- Podがクラスター内で通信する方法、互いを検出する方法、外部からアクセスする方法
![k8sネットワーク](/md/assets/images/k8s-network.png)
- `kube-proxy`
    - 全てのノードで実行されるプロセス
    - API サーバーにクエリを実⾏してクラスター内の新しいサービスについて学習
    - ノードのiptablesを更新して、必要なルーティング情報を提供

#### 5.1. アプリケーションを公開するサービスの作成

```bash
$ kubectl expose deploy/nginx --port 80
$ kubectl describe svc/nginx
```
- 上記ではClusterIPが作成される
- ブラウザ経由でアクセス

```bash
kubectl proxy
open http://localhost:8001/api/v1/namespaces/default/services/nginx/proxy/
```

- サービスが正常に動作しない場合
    - セレクター内のラベルを確認
    - `kubectl get endpoints <service-name>`で確認
    - 生成されていない場合、ポッドを見つけられていない可能性
- k8sはServiceを利用し、全てのノードのiptablesを動的に構成

#### 5.2. サービスの DNS エントリーの確認

- Serviceが作成したDNS登録を確認
    - `$SERVICENAME.$NAMESPACE.svc.cluster.local`
    - 完全修飾ドメイン名

- `nslookup nginx`
    - 例：`nginx.default.svc.cluster.local`
    - 同じ名前空間でないと、結果を返さない

#### 5.3. サービスのタイプの変更

- `LoadBalancer`タイプはコストがかかる可能性

#### 5.4. Ingress コントローラーのデプロイ

- リバースプロキシ、LBとして機能
- ホスト名、URIパスで変更できる

- Ingressコントローラをデプロイ

```bash
$ kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/
 controller-v1.8.1/deploy/static/provider/cloud/deploy.yaml
```
- 新しく作成されたingress-nginx名前空間で新しいポッドが起動
    - `kubectl get pods -n ingress-nginx`
- k8s Gateway APIの新しい仕様がIngress仕様の将来的な代替として登場
    - 今後はこちらを検討する価値がある

#### 5.5. クラスターの外部からサービスにアクセスできるようにする

- hello-appサービスへのURI パス/webを構成するIngressオブジェクト

```yaml
 apiVersion: networking.k8s.io/v1
 kind: Ingress
 metadata:
  name: nginx-public
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
 spec:
  ingressClassName: nginx
  rules:
  - host:
    http:
      paths:
      - path: /web
        pathType: Prefix
        backend:
          service:
            name: web
            port:
              number: 8080
```

- ダッシュボードで確認できる
- 上記の場合は、プライベートIPアドレス
- IngressコントローラーはAPIサーバーの/ingressesエンドポイントをリッスン
- `kubectl describe ingress`
