### 2.コンテナの作成と実行

- Open Container InitiativeがOCIイメージ形式で標準化している

#### コンテナイメージ

- ローカルからイメージをビルド
- コンテナレジストリからイメージをダウンロード
- イメージは複数のレイヤーで構成されている
  - 各レイヤーからファイルを追加、削除、変更

**コンテナの設定**
- ネットワークの設定⽅法
- 名前空間の分離⽅法
- リソース制約(cgroup)
- コンテナインスタンスにどのようなsyscall制限を設定するか

#### Dockerでアプリケーションイメージを構築する

##### ドッカーファイル

- `.dockerignore`ファイルの追加を忘れずに
```plaintext
node_modules
```

##### 画像サイズを最適化する

- イメージの大きさを常に気にする
- 後続のレイヤーによって削除されたファイルは実際にはイメージに含まれることに注意
  - ただアクセスできないだけ
  - プルするたびに、ネットワークを介して送信されてしまう
- レイヤーを変更するたびに、そのあとのレイヤーもすべて変更される
  - 前のレイヤーを変更すると、後ろのレイヤーを再構築、プルする必要
  - `npm install`と`cp server.js .`のどちらを先に書くべきか？
    - `server.js`が変更された場合を考える
    - `node`パッケージを後に書くと、`server.js`の変更ごとにプルする必要
      - 変更される可能性の低いものから書く

##### イメージ・セキュリティー

- 例えば、PWを含んだコンテナを作らない
- 一個のレイヤーでファイルを削除しても、その前のレイヤーからは削除されない
- イメージは実行することが目的なので、最小化が重要
  - 不要なライブラリなど、無駄な脆弱性を残さない

#### 多段階イメージビルド

- 大きいイメージはデプロイが遅くなる
```dockerfile
...

FROM alpine
USER nobody:nobody
COPY --from=build /go/bin/kuard /kuard
CMD [ "/kuard" ]
```
- ビルドイメージとデプロイイメージで分ける
- 500MB→20MBまでこの例では削減できた
  - デプロイ時間の大幅な短縮

マルチステージビルドは有名ですが、ここまでサイズが変わるとは思いませんでした。また、`USER`や`ENV`はあまり使用したことがなかったので意識したいです。

#### リモートレジストリに画像を保存する

- Gitと同様に、Dockerレジストリにも様々な選択肢
  - セキュリティ、コラボレーション機能で選ぶ
- プライベート、パブリックリポジトリ

#### コンテナ・ランタイム・インターフェイス

##### Dockerでコンテナを実行する

##### クアード・アプリケーションを探る

##### リソースの使用を制限する

- 内部的には`cgroup`の機能で実装されている
```bash
  --memory 200m \
  --memory-swap 1G \
  --cpu-shares 1024 \
```

`docker-compose.yaml`だけでなく、`docker`コマンドでもリソースを制限できるのは知りませんでした。

#### クリーンアップ

- `docker system prune`
  - 全てのイメージを削除するコマンド
  - cronジョブで実行する方法もある

#### Kubernetesクライアント

##### クラスタの状態をチェックする

```bash
$ kubectl get componentstatuses
```

- `scheduler`と`etcd`サーバーを確認できる

##### Kubernetesノードをリストアップする

- `kubectl get nodes`→`kubectl describe nodes`の流れ

  - System-info

```bash
kubectl get daemonSets --namespace=kube-system kube-proxy
```

##### Kubernetes DNS
```bash
kubectl get deployments --namespace=kube-system core-dns
kubectl get services --namespace=kube-system core-dns
```

```

#### Kubernetes APIオブジェクトを表示する

- k8sリソースはRestFulリソースを提供

- `-o wide`: 詳細

#### Kubernetesオブジェクトを作成、更新、破棄する

#### オブジェクトにラベルと注釈を付ける

- `--overwrite`フラグで上書き
- `ラベル名-`でラベルの削除

#### デバッグ・コマンド

- Podに複数のコンテナがある場合は`-c`でコンテナを選択
- `logs`と`exec -it --bash`コマンド
- bashがない場合は、`kubectl attach -it pod`
- `kubectl port-forward <pod-name> 8080:80`
  - ローカルのポート8080:リモートの80
- `kubectl get events`
  - `--watch`
  - 全ての名前空間は`-A`
- `kubectl top pods`

#### コマンド自動補完

#### Podを使って考える

$ kubectl run kuard --generator=run-pod/v1 \

$ kubectl delete pods/kuard
```

コマンドで作成することはあまりないと思いますが、一応オプションなども覚えておきたいです。

#### 正常性確認

- デフォルトでは、メインプロセス軌道を確認するだけ

##### ライブネス・プローブ

```yaml
      livenessProbe:
        httpGet:
          path: /healthy
          port: 8080
        initialDelaySeconds: 5
        timeoutSeconds: 1
        periodSeconds: 10
        failureThreshold: 3
```
- httpGetプローブの使用
- コンテナ起動5行後から呼び出される
- 1秒以内に応答する必要(200-400)
- 3回連続失敗でコンテナは再起動
```bash
kubectl port-forward kuard 8080:8080
```
- ブラウザで、http://localhost:8080にアクセス
  - Liveness Probeを選択
  - コンテナを再起動できる
- 実際の再起動の動作はPodの`restartPolicy`で決定される
  - `Always`, `onFailure`, `Never`

##### レディネスプローブ

- 稼働状態と準備状態を区別する
  - readinessプローブとliveness プローブを組み合わせる

##### スタートアップ・プローブ

- スロースタートコンテナを管理する代替⽅法

##### 高度なプローブ設定

- プローブを開始するまでの待機時間
- 真の失敗と⾒なすべき失敗の数
- 失敗数をリセットするために必要な成功の数など 

##### その他の正常性確認型チェック

- tcpSocketヘルスチェックもサポート
  - 非HTTPアプリで役立つ
- execプローブ
  - スクリプトが0コードを返した場合に成功
  - カスタムアプリ検証ロジックに役立つ

#### リソース管理

##### リソースの要求最低限必要なリソース

- CPUとメモリを考える
- CPU半分以上、128メモリ以上のリクエストの例
```yaml
resources:
  requests:
    cpu: "500m"
    memory: "128Mi"
```
- requestsは最小値であることに注意

k8sでも`docker-compose.yaml`みたいに書けるのは知りませんでした。

##### リソースの使用量を制限する
```yaml
      resources:
        requests:
          cpu: "500m"
          memory: "128Mi"
        limits:
          cpu: "1000m"
          memory: "256Mi"
```
- 1000m = 1.0CPU

#### ボリュームでデータを永続化する

- Podの削除、再起動でファイルシステムのデータも消える
  - ステートレスWebアプリでは問題ない

##### Podでボリュームを使用する

- `spec.volumes`, `container.volumeMounts`の編集
- pod内の異なるコンテナは、異なるマウントパスで同じボリュームをマウントできる

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: kuard
spec:
  volumes:
    - name: "kuard-data"
      hostPath:
        path: "/var/lib/kuard"
  containers:
    - name: kuard
      image: gcr.io/kuar-demo/kuard-amd64:blue
      volumeMounts:
        - mountPath: "/data"
          name: "kuard-data"
      ports:
        ...
```

##### Podでボリュームを使うさまざまな方法

- 真に永続的なデータの保存
  - NFS, iSCSIのプロトコル
  - EBSなど

- NFSサーバの例
```yaml
 volumes:
    - name: "kuard-data"
      nfs:
        server: my.nfs.server.local
        path: "/exports"
```

#### すべてをまとめる

- 永続ボリューム、レディネスプローブとライブネスプローブ、リソース制限の組み合わせ
```yaml
apiVersion: v1
 kind: Pod
 metadata:
  name: kuard
 spec:
  volumes:
    - name: "kuard-data"
      nfs:
        server: my.nfs.server.local
        path: "/exports"
  containers:
    - image: gcr.io/kuar-demo/kuard-amd64:blue
      name: kuard
      ports:
        - containerPort: 8080
          name: http
          protocol: TCP
      resources:
        requests:
          cpu: "500m"
          memory: "128Mi"
        limits:
          cpu: "1000m"
          memory: "256Mi"
      volumeMounts:
        - mountPath: "/data"
          name: "kuard-data"
      livenessProbe:
        httpGet:
          path: /healthy
          port: 8080
        initialDelaySeconds: 5
        timeoutSeconds: 1
        periodSeconds: 10
        failureThreshold: 3
      readinessProbe:
        httpGet:
          path: /ready
          port: 8080
        initialDelaySeconds: 30
        timeoutSeconds: 1
        periodSeconds: 10
        failureThreshold: 3
```
